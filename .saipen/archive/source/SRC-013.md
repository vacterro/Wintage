PROJECT: Wintage

MODE: ROADMAP / PARKED FEATURE SPEC

FEATURE:
User-configurable Scenario Presets.

IMPORTANT:

Do NOT implement this feature while T-246 / SRC-007 remains active.

Finish the existing audit convergence first.

After T-246 is terminal, claim this as the next independent feature ticket.

GOAL:

Allow the user to save the current Wintage installer configuration as a named reusable preset and restore it later.

A preset represents desired installer UI state, not a second installation engine.

The existing install.ps1 / batch Apply / Revert paths remain the only execution paths.

CORE USER FLOW:

1. User selects a palette.
2. User checks any combination of available targets.
3. User chooses "Save preset".
4. User names it, for example:

   * Work
   * Creative
   * Minimal
   * Browsers
   * Everything
   * Test VM
5. Later the user selects that preset.
6. Wintage restores:

   * palette;
   * target selection;
   * supported preset options.
7. User presses the existing Apply or Revert button.

Selecting a preset MUST NOT immediately mutate applications.

Preset selection stages intent in the GUI.
Existing Apply/Revert buttons execute that intent.

ARCHITECTURE:

Store user presets outside the repository:

%APPDATA%\Wintage\presets\

Use one JSON file per preset.

Example conceptual schema:

{
"schemaVersion": 1,
"id": "work",
"name": "Work",
"description": "",
"palette": {
"type": "pack",
"slug": "goldendefault"
},
"targets": [
"windows",
"terminal",
"totalcmd",
"vscode",
"brave"
],
"options": {}
}

CUSTOM PALETTE SNAPSHOTS:

If the active palette is an unsaved Custom working palette, saving a preset must capture its complete canonical token set.

Conceptual form:

{
"palette": {
"type": "snapshot",
"tokens": {
"...": "..."
}
}
}

The snapshot must contain exactly the canonical theme-schema token set.

Do not depend on themes/custom.json continuing to contain the same values.

When such a preset is loaded:

* populate the existing Custom working palette;
* select Custom in the GUI;
* do not mutate repository files merely by loading the preset;
* actual Apply continues through the existing custom-palette installation path.

TARGET IDENTITY:

Persist canonical target keys, never display labels.

Good:

"totalcmd"
"terminal"
"cinema4d"

Bad:

"Total Commander   themed"

Display text and installation state can change.
Target keys are the identity contract.

UNAVAILABLE TARGETS:

A preset is allowed to reference a target not currently installed or unavailable on this machine.

Loading such a preset must:

* keep the target in the preset definition;
* not silently remove it;
* not check an unavailable target;
* clearly report unavailable preset members in the GUI/status/log.

Example:

Preset "Creative" loaded.
5 targets selected.
2 unavailable: cinema4d, obs.

A later machine where those targets exist must still be able to use the same preset.

PATH-BASED TARGETS:

Do NOT persist source/install paths inside presets.

CodeNomad, WorkBuddy, portable-browser roots and similar machine-specific paths remain owned by the existing paths.json preference subsystem.

When loading a preset containing a path-backed target:

* use the existing remembered path;
* if no valid remembered path exists, leave the target unavailable/unselected;
* report why.

Do not open folder dialogs merely because a preset was selected.

PRESET FILE SAFETY:

Preset persistence must be fail-safe.

Requirements:

* UTF-8 without BOM;
* strict schema validation;
* atomic temp-file + replace/move write;
* no partially written preset may replace a valid preset;
* malformed preset must not prevent WintageInstaller from opening;
* one corrupt preset must not hide healthy presets;
* reject duplicate preset IDs after case normalization;
* safe filename generation;
* preset filename must not allow path traversal;
* unknown future schema versions fail with a useful message.

Prefer a shared presets.lock under:

%APPDATA%\Wintage\presets.lock

so future CLI support cannot introduce lost-update races.

Do not use repository files as user preference storage.

GUI:

Add a compact Preset surface to the Themes tab.

Minimum controls:

* preset ComboBox;
* Save As;
* Update;
* Rename;
* Delete.

Recommended behavior:

* selecting a preset loads it immediately into palette + target checkboxes;
* this is UI-state restoration only;
* Apply/Revert remain explicit operations.

Do not add a second Apply engine.

Provide a visible state for:

* no preset selected;
* modified since preset load;
* unavailable targets;
* invalid/missing palette.

Example:

Preset: Creative *
^ modified locally

The modified marker appears when palette or checked targets differ from the loaded preset.

SAVE AS:

* prompt for a non-empty name;
* derive a safe stable ID;
* reject or explicitly resolve name collisions;
* save current palette + checked target keys.

UPDATE:

Overwrite only the currently selected user preset.

Require explicit confirmation if destructive overwrite behavior is involved.

RENAME:

Rename metadata and backing file atomically enough that failure cannot lose the original preset.

DELETE:

Require confirmation.

Deleting a preset changes no installed application state.

It only removes the preset definition.

BUILT-IN STARTER PRESETS:

Do not hardcode machine-specific app assumptions.

It is acceptable to provide a few generated convenience presets whose membership is resolved from current discovery, for example:

* All available
* Browsers
* Development
* Creative
* Minimal Windows

But these must be clearly distinguishable from editable user presets.

An even safer first release is USER PRESETS ONLY.
Built-ins can be a later feature.

DO NOT STORE IN V1:

* remembered filesystem paths;
* secrets;
* API keys;
* arbitrary commands;
* PowerShell snippets;
* environment variables;
* BetterDiscord plugin mutations;
* FreeBuff sound file contents;
* logon-task side effects;
* automatic Apply-on-load;
* automatic Revert-on-load.

These may become explicit future preset option types after the base contract is stable.

PRESET PORTABILITY:

The JSON format should intentionally be human-readable and copyable between machines.

Do not include:

* absolute repository path;
* username;
* machine name;
* timestamps required for semantics.

Optional created/modified timestamps are acceptable metadata only.

VALIDATION:

Create a dedicated preset schema/parser rather than scattering ConvertFrom-Json assumptions through click handlers.

Validate:

* schemaVersion;
* id;
* name;
* palette type;
* palette slug or complete custom token snapshot;
* target key array;
* duplicates;
* invalid types;
* unsafe IDs.

UI code consumes only validated preset objects.

TESTS:

Create a dedicated preset regression suite.

At minimum cover:

1. Save pack-based preset.
2. Reload installer and load preset.
3. Palette restored.
4. Exact target set restored.
5. Custom palette snapshot round-trip.
6. Missing target retained but reported unavailable.
7. Path-backed target without remembered path does not open a dialog.
8. Missing palette fails visibly and does not silently select Golden Default.
9. Malformed JSON does not crash installer.
10. Unsupported schema version rejected.
11. Unknown target preserved as unavailable.
12. Duplicate targets rejected or canonicalized deterministically.
13. Atomic write failure preserves previous preset bytes.
14. Rename failure preserves original preset.
15. Delete changes no installation manifest/application state.
16. Loading preset performs no child install process.
17. Loading preset performs no repository mutation.
18. Apply after preset load uses the existing ONE batch worker.
19. Revert after preset load uses the existing ONE batch worker.
20. GUI modified marker reacts to palette/target changes.

RED CONTROLS:

Include mutation/red controls proving:

* preset load never invokes install.ps1 Apply/Revert;
* malformed preset cannot silently become a default preset;
* failed overwrite cannot destroy the previous preset;
* unavailable target is not silently removed from the saved definition.

ACCEPTANCE:

* User can create multiple named scenario presets.
* Presets survive restart.
* Presets are portable between machines.
* Standard palette and custom-token scenarios round-trip.
* Arbitrary target combinations round-trip.
* Unavailable targets degrade visibly and safely.
* Loading is side-effect free.
* Existing Apply/Revert transaction paths remain authoritative.
* No duplicated target installation logic is introduced.
* Existing audit/test matrix remains green.

NON_GOALS FOR FIRST PRESET RELEASE:

* arbitrary workflow scripting;
* scheduled presets;
* automatic application launch/close;
* automatic Apply on preset selection;
* per-preset filesystem paths;
* per-preset credentials;
* preset cloud sync;
* import/export UI beyond copying the JSON file;
* BetterDiscord plugin scenarios;
* FreeBuff sound scenarios;
* logon-task scenarios.

FUTURE EXTENSION CONTRACT:

Reserve the top-level "options" object for typed future scenario settings.

Examples that may later be added deliberately:

* freebuff completion sound policy;
* BetterDiscord plugin set;
* logon-task policy;
* target-specific options;
* Apply-on-startup behavior;
* scheduled scenario switching.

Unknown option fields must never execute arbitrary behavior.

They should be ignored only if the schema explicitly permits forward compatibility, otherwise fail validation.

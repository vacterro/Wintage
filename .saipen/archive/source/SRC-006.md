EVIDENCE:

  second Apply rc=0;
  second Revert rc=0;
  resulting settings were Stock-A/111, not Stock-B/222.
- Root cause of that data loss is install-terminal.js:515-523: Apply captures a new pre-state only when neither `.wintage.bak` nor `.wintage-created` exists. The failed finalization leaves the OLD recovery artifact behind, so the next Apply silently reuses a snapshot from the previous ownership cycle.

The Windows Terminal transaction has no coherent persisted ownership-state transition between "manifest owns themed file", "reverted but rollback-capable", and "manifest removed/recovery consumed". The marker is simultaneously treated as proof of manifest ownership and as recovery state, yet removing the manifest does not transition the marker. The absent-original-file rollback additionally assumes a reverted file must still exist, which is false by design.

- If manifest removal fails, re-theme every member of `$revertedItems` regardless of whether settings.json currently exists. The helper already has enough information to recreate a file that Wintage originally created; the `Test-Path $settings` guard must not suppress rollback.

[P0] [W2-001] desktop/install.ps1:generic VS Code-family recovery lifecycle at $recoveryMeta/$pristineDir
EVIDENCE:
- Generic extension targets persist recovery under `recovery\<target>\recovery.json` and `pristine` (desktop/install.ps1:874-881).
- Apply captures a pristine baseline only when `recovery.json` does not already exist (desktop/install.ps1:941-954). The comment calls this "first-ever apply", making the persisted recovery record the gate that decides whether a new ownership epoch gets a fresh baseline.
- Revert restores/removes the destination and commits `Remove-ManifestEntry`, but after that successful commit there is no removal or retirement of `recovery.json` or `pristine` (desktop/install.ps1:883-929). Execution immediately continues to the next target.
- Therefore a complete cycle deterministically leaves the old ownership epoch alive:
  epoch 1 user tree A -> Apply captures A -> Revert restores A and removes the manifest but leaves recovery(A);
  user changes the tree to B -> epoch 2 Apply sees the old recovery record and skips baseline capture;
  epoch 2 Revert restores stale A, destroying post-epoch-1 state B.
- The same branch also conflates invalid/incomplete replaced recovery with Wintage-created state. At desktop/install.ps1:895-905, only `mode == 'replaced' AND pristine exists` enters restoration. Every other state falls into `else`, removes `$dest`, and reports it as "Wintage-created". Thus a legitimate `mode: replaced` record whose pristine directory is missing causes destructive deletion instead of fail-closed recovery.
- `mode` and `target` are parsed but not validated before mutation. A malformed/foreign mode reaches the same destructive `else`.
- The project already implements the intended lifecycle elsewhere: BetterDiscord explicitly throws when `mode == replaced` but pristine recovery is missing (desktop/modules/targets.ps1:1962-1969), consumes recovery only after manifest removal succeeds (1975-1981), and stamps recovery provenance on creation (2011-2017). qBittorrent likewise preflights missing pristine before mutation (2568-2578) and has explicit recovery consumption. The generic target path has drifted from those invariants.
- tools/test-reapply.ps1 test 30 verifies only one Apply/repaint/Revert sequence (approximately lines 798-829). It confirms the original tree and manifest restoration but never asserts that recovery is consumed and never starts a second ownership epoch, so the stale-baseline defect remains invisible.
DEFECT:
Generic VS Code-family extension recovery has no completed-epoch transition. Recovery is treated as permanent first-touch authority even after a successful Revert has removed ownership from the manifest. A later installation epoch consequently inherits a stale user snapshot and can restore obsolete bytes over newer user state. Additionally, recovery metadata is not fail-closed: `replaced + missing pristine`, unknown modes, and malformed ownership states are interpreted as `created`, allowing deletion of the live destination exactly when restoration evidence is incomplete. This is a direct user-data-loss path.
REPAIR:
- Treat persistent recovery as belonging to one manifest ownership epoch, not to the target forever.
- Before any Revert mutation, parse and validate recovery metadata completely: accepted modes must be exactly `created` or `replaced`; `target` must match the current target; if `mode == replaced`, pristine recovery must exist and be readable. Any contradictory/unknown/incomplete state must throw before `$dest` is touched.
- After the target restoration/removal AND `Remove-ManifestEntry` commit succeed, consume/retire `recovery.json` and `pristine`. Do this only after the manifest transition so failed commits retain recovery for retry.
- If recovery provenance/epoch stamping is the project-standard ownership mechanism, apply the existing provenance contract here rather than inventing filename-based authority.
- On a manifest-commit failure, restore `$dest` to its complete themed pre-Revert state and retain the old recovery epoch unchanged.
- A subsequent Apply after a complete Revert must therefore see no active recovery record and capture the then-current user tree as a fresh baseline.
VERIFY:
- Two-epoch regression: seed tree A -> Apply -> Revert -> confirm manifest absent AND recovery epoch consumed -> modify tree to byte-distinct B -> Apply -> Revert. Final tree must equal B byte-for-byte and contain no bytes restored solely from A.
- Repaint within ONE ownership epoch must still preserve the same pristine baseline: A -> Apply palette 1 -> Apply palette 2 -> Revert => A.
- `mode: replaced` with missing pristine must fail nonzero before mutation; destination bytes, manifest entry and recovery metadata must remain unchanged.
- Unknown mode, mismatched target, corrupt JSON and foreign recovery provenance must all fail before mutation.
- `mode: created` must remove only the Wintage-created destination; after a successful manifest transition its recovery state must be consumed.
- Inject `WINTAGE_TEST_FAIL_MANIFEST_MOVE` during Revert: destination must return to the complete themed pre-operation state, manifest and recovery must remain retryable, and a clean retry must finish and consume recovery.

[P1] [W2-002] desktop/install.ps1:-Reapply snapshot -> child dispatch / Enter-TargetLock boundary
EVIDENCE:
- `-Reapply` reads the complete manifest once at desktop/install.ps1:233-242 and stores that snapshot in `$manifest`.
- It then iterates the snapshot's keys and derives both health and desired palette from stale `$data = $manifest[$key]` (265-276).
- For an unhealthy entry it launches a new explicit `install.ps1 -Target <key> -Palette <snapshot palette>` child (274-303).
- The parent does not own the target mutex while deciding or spawning. The target mutex is acquired only inside the child target dispatcher at desktop/install.ps1:649-660.
- Acquiring the target mutex serializes mutations, but after acquisition the child performs only a generic `Read-Manifest` validity check. It does not verify that the target entry still exists or that its palette/applied identity still matches the Reapply snapshot that authorized the child.
- Consequently the following ordering is legal under the current locks:
  1. background Reapply reads target X with palette A;
  2. another process acquires X's target lock and successfully Reverts X, removing its manifest entry;
  3. stale Reapply child later acquires X's lock;
  4. child applies palette A from the old snapshot and recreates the manifest entry.
  A user-completed Revert is therefore resurrected.
- An equivalent last-writer-intent violation exists for palette changes:
  Reapply snapshots palette A -> user explicitly Applies palette B and commits -> stale child later acquires the lock and Applies A. The older background decision overwrites the newer explicit user choice.
- Manifest locking in common.ps1:192-229 correctly protects manifest read-modify-write, and the per-target mutex at 231-265 correctly serializes target mutation. Neither lock provides compare-and-swap semantics between the Reapply parent's decision snapshot and the child's later mutation.
- Existing Reapply regression coverage exercises stale paths/health and child failure behavior, but repository search found no synchronization test in which the manifest entry is removed or changed after the parent snapshot and before the child obtains target ownership.
DEFECT:
The concurrency model serializes execution but not intent. Reapply computes work from an unlocked historical manifest snapshot and the later target-locked child never revalidates that snapshot. A background/logon Reapply can therefore undo a newer successful Revert or palette Apply performed by another process. The mutex prevents simultaneous writes while still permitting stale writes in sequence, which is the more irritating species of concurrency bug because every individual lock looks respectable.
REPAIR:
- Bind every Reapply child invocation to the exact manifest entry that authorized it.
- Pass an immutable expected-entry identity into the child, using fields already available in the snapshot such as target + palette + applied timestamp + resolved path/payload identity, or an explicit deterministic entry revision.
- Immediately AFTER `Enter-TargetLock` and BEFORE any target mutation, re-read the current manifest and compare that target's current entry with the expected Reapply identity.
- If the entry disappeared, treat the Reapply work item as superseded and skip without recreating ownership.
- If the entry changed, treat it as superseded and skip rather than applying the older palette/path decision.
- Only an unchanged expected entry may proceed through the existing health/preflight/mutation path.
- Preserve current sibling independence and target->manifest lock order. Do not hold the parent target mutex while spawning a child unless dispatch is redesigned to avoid self-deadlock.
- Report superseded work distinctly from target failure so `-Quiet` background execution does not convert a normal concurrent user decision into an error.
VERIFY:
- Deterministic race fixture with synchronization barriers, not sleeps: Reapply snapshots X/A; pause before child target ownership; concurrently Revert X to completion; resume Reapply. Final target must remain reverted and X must remain absent from manifest.
- Same fixture with concurrent explicit Apply X/B. After B commits, resumed stale Reapply A must skip; live target and manifest must remain B.

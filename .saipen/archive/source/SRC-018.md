[P1] [CORE-001] desktop/WintageInstaller.ps1::Save-CurrentAsPreset / Refresh-Presets / preset action handlers
EVIDENCE:
- Save-CurrentAsPreset writes the new preset, then calls Refresh-Presets at lines 2104-2105, and only afterwards assigns `$script:activePresetId = $id` at line 2106.
- Refresh-Presets lines 2086-2088 selects the ComboBox item using the PREVIOUS activePresetId.
- Therefore Save As while preset A is active can leave the ComboBox visibly showing A while internal activePresetId points to newly created B. Saving with no previous active preset can leave the ComboBox visually unselected while activePresetId points to the new preset.

DEFECT:
Preset identity has two independent owners: visible ComboBox selection and activePresetId. Save As can desynchronize them, after which Update/Rename/Delete can operate on a different preset from the one the GUI appears to have selected. In the delete path this can remove the wrong user preset. Display-name lookup adds a second identity ambiguity for otherwise valid presets with distinct IDs but equal names.
REPAIR:
Create one canonical activation routine that accepts a preset ID/object and atomically updates activePresetId, ComboBox selection and baseline. Bind ComboBox entries to stable preset IDs/objects rather than using the display name as identity. After Save As and Update, refresh the collection and explicitly activate the saved ID through that routine. Rename/Delete must derive their target from the same canonical selected identity and fail closed if visible/internal state cannot be reconciled.
VERIFY:
Add GUI/controller regressions for: no-active Save As -> new preset visibly selected; A -> Save As B -> B visibly and internally active; immediate Update affects B; immediate Rename affects B; immediate Delete confirmation names and deletes B; two valid presets with equal display names remain individually selectable by ID.

[P0] [CORE-001] tools/electron-fuses.js:defuse + tools/install-electron.js:restoreFuseBackupForRevert
EVIDENCE: `defuse()` preserves the first `<exe>.wintage-fuse.bak` indefinitely (`electron-fuses.js:128-134`), while every real revert blindly copies that backup over the current executable (`install-electron.js:395-402`), including the `updated-relocated` path (`372-388`). Focused real-helper reproduction: Apply against v1 created a backup byte-identical to the v1 EXE; a simulated vendor update then replaced both root `app.asar` and the EXE with distinct fused v2 bytes; `--status-json` correctly reported `updated-relocated`, version `2.0.0`, with the live EXE still byte-identical to v2; `--revert` returned rc=0 but afterward the EXE was byte-identical to v1, not v2, and the backup had been deleted. The existing state test changes the ASAR version but not the executable generation, so its “restores v2, never v1” assertion does not cover this case.
DEFECT: The fuse backup is treated as install-epoch authority without any executable-generation identity. A vendor update can replace the executable while the old fuse backup survives; Revert then silently overwrites the fresh executable with an older binary while reporting a successful return to current stock state. This can downgrade/corrupt the application and can also reintroduce an older security-sensitive executable.
REPAIR: Bind fuse recovery to the executable generation. Before reusing/restoring a backup, compare current and backup binaries while ignoring only the explicitly owned fuse-byte positions, or persist and validate equivalent executable identity metadata. If the current executable differs outside those owned fuse bytes, the backup is stale and must never overwrite it. Reapply against a new vendor executable must establish the current stock executable as the new recovery authority before defusing it; Revert from an `updated-*` state must leave the current vendor executable intact. Legacy backups without metadata must be validated by binary comparison and fail closed when identity is ambiguous.
VERIFY: Extend `tools/test-electron-state.js` with relocation and in-place fixtures where v1 Apply creates a fuse backup, then BOTH `app.asar` and EXE are replaced by distinct v2 stock bytes. Revert must preserve/restore the exact v2 EXE, never v1. Reapply must rotate recovery to v2, defuse v2, and a subsequent Revert must restore v2 byte-identically.

[P0] [CORE-002] tools/electron-fuses.js:defuse
EVIDENCE: After creating the recovery backup, `defuse()` overwrites the live executable directly with `fs.writeFileSync(exe, data)` (`electron-fuses.js:136-137`) and merely returns an error if that write throws. A focused fault injection made that call write half the buffer and then throw `EIO`. `defuse()` returned `could not write ...`, the recovery backup remained byte-identical to the original, but the live EXE shrank from 130 bytes to 65 bytes and was no longer equal to the original.
DEFECT: Fuse mutation is not atomic and the error path does not restore the live executable. A short/partial filesystem write can therefore turn a recoverable fuse operation into a truncated application EXE while the caller only sees an ordinary install failure.
REPAIR: Never write fuse changes directly into the live EXE. Write the complete modified Buffer to a same-directory temporary file, read/verify its exact bytes and fuse verdict, then replace the live file atomically. If replacement itself fails, the original executable must remain untouched; if a platform-specific replacement sequence can mutate the destination before failing, explicitly restore the in-memory original/validated backup and surface rollback failure. Reuse or extend the project’s atomic-write machinery for binary content rather than duplicating another unsafe writer.
VERIFY: Add fault injection for short temp write, temp verification failure, rename/replace failure and successful replacement. Every failed case must leave the live EXE byte-identical to pre-operation and preserve the pre-operation backup state; success must alter only the intended fuse bytes.

[P1] [CORE-003] tools/install-electron.js:installInPlace
EVIDENCE: `installInPlace()` reads prestate, then copies the current ASAR to `app.asar.bak` at `545-550` before calling `ensureDefused(resolveExe())` at `559`. `ensureDefused()` can terminate the process on an unverifiable fuse state, so this mutation occurs outside the later transaction `try` beginning at `561`. Focused real-helper reproduction with a valid stock ASAR and an EXE carrying unknown fuse schema version 2 returned rc=1 with the intended “refusing to modify” message; the live ASAR stayed unchanged but `app.asar.bak` had nevertheless been created and was byte-identical to the ASAR. In `updated-inplace`, the same ordering can overwrite a pre-existing rollback backup before the fuse preflight rejects the operation. The later catch also restores ASAR/sidecars/fuses but does not restore the pre-operation `.bak`.
DEFECT: In-place installation mutates rollback authority before the fail-closed fuse preflight and outside the transaction boundary. A rejected or later-failed operation can therefore alter/create `.bak` despite promising no mutation, and an updated install can replace previous recovery authority without successfully completing the new generation.
REPAIR: Split fuse handling into a pure verdict/preflight phase and a mutation phase. Resolve the EXE and prove that its fuse schema is supported before ANY `.bak`, sidecar, ASAR or EXE write. Snapshot `.bak` existence+bytes as part of the transaction, then perform backup rotation, fuse mutation, sidecars and ASAR patching inside the same rollback scope. Avoid `process.exit()` from inside transaction-capable helpers; propagate errors to one rollback owner.
VERIFY: For stock and `updated-inplace`, test unknown/malformed/missing/ambiguous fuse states with `.bak` initially absent and pre-existing. Every refusal must leave ASAR, EXE, `.bak` and sidecars byte-for-byte/existence-identical. Inject failures after backup rotation and after fuse mutation and require the same exact-prestate invariant.

[P0] [CORE-001] desktop/install.ps1:913-984 generic VS Code-family recovery epoch

EVIDENCE:
- Revert treats recovery.json existence as authority but performs no schema validation:
  - lines 925-926 parse recovery.json;
  - lines 927-931 restore pristine only when `mode == 'replaced'` AND pristine exists;
  - every other state falls through lines 932-934 and recursively deletes `$dest` while claiming it was "Wintage-created".
  Therefore `mode='replaced'` with a missing pristine directory, an unknown/corrupt mode, or an otherwise incomplete ledger is interpreted destructively instead of failing closed.
- After the successful restore/removal, lines 936-938 remove the manifest entry but do NOT consume, retire, rename or otherwise close `$recoveryDir`, `$recoveryMeta` or `$pristineDir`.
- The next Apply at lines 972-984 captures a baseline only when recovery.json does not exist. Because a successful prior Revert leaves it behind, every later ownership cycle silently reuses the first cycle's baseline.
- tools/test-reapply.ps1 test 30 covers Apply -> repaint -> Revert once, but ends after checking manifest removal. It never checks recovery retirement and never executes a second Apply/Revert lifecycle.

DEFECT:
The generic VS Code-family recovery ledger has no completed-epoch state. A normal successful Revert leaves first-touch recovery permanently authoritative. After the user changes the restored directory, a later Apply followed by Revert removes the current directory and restores stale first-cycle bytes, losing user changes. Independently, incomplete/corrupt `replaced` recovery can fall into the destructive "created" branch and delete the live directory. This is direct user-data-loss territory.

REPAIR:
- Introduce strict recovery schema validation before any mutation:
  - object root only;
  - target must equal the current target;
  - mode must be exactly `created` or `replaced`;
  - `replaced` requires a complete readable pristine directory;
  - unknown/missing/incomplete recovery must FAIL CLOSED with manifest/live directory untouched.
- Give recovery an explicit lifecycle. On successful Revert use the already-established retire-first pattern:
  1. atomically rename the active recovery directory to a unique tombstone before manifest removal;
  2. if manifest removal fails, rename it back before reporting rollback success;
  3. after manifest removal commits, delete the tombstone;
  4. the next Apply must therefore capture a fresh baseline.
- Do not delete the live destination merely because metadata is malformed or recovery material is missing.
- Keep explicit legacy detection separate from recovery-based ownership.

VERIFY:
- Add a two-cycle fixture:
  1. user directory A -> Apply -> Revert;
  2. assert active recovery epoch is gone;
  3. user changes A to B/adds new files;
  4. Apply -> Revert;
  5. assert exact B bytes/tree are restored, with no first-cycle files resurrected.
- Corrupt-mode fixture: recovery.json `{mode:"garbage"}` -> Revert exits nonzero, destination and manifest byte-identical.
- Missing-pristine fixture for `mode:"replaced"` -> exits nonzero, destination/manifest untouched.
- Inject manifest-commit failure after recovery retirement -> active recovery is restored and retry remains possible.
- Run tools/test-reapply.ps1 + tools/test-dir-prestate.ps1 + tests/Run-Tests.ps1.

[P1] [CORE-002] desktop/install.ps1:237-328,679-690 -Reapply intent race

EVIDENCE:
- `-Reapply` reads one manifest snapshot at lines 237-246.
- For each target it copies `$data` from that historical snapshot and decides health at lines 269-278.
- It constructs a child invocation using the stale target/palette at lines 279-281 and may wait arbitrarily long before the child acquires its own target lock.
- The actual mutation process acquires the per-target mutex only at lines 679-685.
- After acquiring it, line 690 merely calls `Read-Manifest` to prove the manifest is syntactically valid. It does NOT verify that:
  - the target entry still exists;
  - the palette still equals `$data.palette`;
  - the recorded path/version/applied generation is still the entry that caused Reapply.
- The child then proceeds as an ordinary explicit Apply and can call Set-ManifestEntry, recreating whatever stale intent the parent captured.

DEFECT:
Execution is serialized, but intent is not. Race:
1. background/logon `-Reapply` reads target X with palette A;
2. explicit user operation acquires X's target lock, Reverts X or changes it to palette B, then releases the lock;
3. stale Reapply child acquires the lock afterward;
4. it never revalidates its historical manifest intent and applies A.
A completed Revert can therefore be resurrected, and a newer explicit palette choice can be overwritten by an older background decision.

REPAIR:
- Revalidate Reapply intent INSIDE the target lock immediately before any discovery/mutation.
- Preferred shape: parent passes an internal expected-manifest fingerprint/generation containing at least target existence + palette + canonical path/items + appVersion/payloadVersion/applied (or a stable digest of the full entry).
- After Enter-TargetLock, child re-reads the current manifest and:
  - if entry disappeared: report "stale Reapply intent; target was reverted", perform zero mutation;
  - if entry differs: report "stale Reapply intent; newer explicit state wins", perform zero mutation;
  - only an exact match may continue.
- Explicit normal `-Target` operations must remain unaffected.
- Do not solve this by widening the manifest lock across child execution; preserve TARGET -> MANIFEST lock ordering and avoid a cross-process deadlock.

VERIFY:
- Deterministic barrier fixture:
  1. Reapply snapshots palette A and pauses before child target-lock acquisition;
  2. concurrent explicit Revert commits;
  3. release Reapply;
  4. assert no target mutation and no resurrected manifest entry.
- Second fixture substitutes an explicit palette B Apply; stale A must not overwrite B.
- Existing concurrent same-target serialization and concurrent-manifest-writer tests must remain green.
- Run tools/test-reapply.ps1 + tools/test-ownership.ps1 + tests/Run-Tests.ps1.

# Wintage για εφαρμογές επιφάνειας εργασίας

Το userscript θέτει θέμα στο διαδίκτυο. Αυτό θέτει θέμα στα προγράμματα γύρω του, από τις ίδιες παλέτες, ώστε ο browser και οι εφαρμογές να σταματήσουν να διαφωνούν για το τι σημαίνει σκούρο χρυσό.

Υπάρχει ένας κανόνας πίσω από κάθε απόφαση εδώ: **οι εφαρμογές ενημερώνονται μόνες τους, και μια ενημέρωση δεν πρέπει να σπάει κάτι σιωπηλά.** Όπου ένας στόχος έχει θέση στο δικό σου προφίλ, το θέμα πηγαίνει εκεί και επιβιώνει των ενημερώσεων. Όπου δεν έχει, ο εγκαταστάτης είναι γραμμένος για να εκτελείται ξανά — και το λέει, αντί να προσποιείται ότι διατηρήθηκε.

## Το GUI

Κάντε διπλό κλικ στο **`Wintage Installer.vbs`** στη ρίζα του repo για να το ανοίξετε χωρίς παράθυρο κονσόλας, ή εκτελέστε αυτό απευθείας για διαγνωστικά:

```powershell
powershell -File desktop\WintageInstaller.ps1
```

Λίστα θεμάτων με χρωματικά δείγματα, οι στόχοι που βρέθηκαν σε αυτό το μηχάνημα, μια ζωντανή προεπισκόπηση Win95 και όλα τα είκοσι ένα χρωματικά tokens ως επεξεργάσιμα δείγματα. Η επεξεργασία οποιουδήποτε δείγματος διακλαδώνει την παλέτα σε **Custom** αντί να αλλάζει ένα παραδοτέο θέμα κρυφά από κάτω σου. Ο πίνακας στα δεξιά δείχνει ζωντανή αντίθεση WCAG για τα τρία tokens που φέρουν κείμενο — μια παλέτα που FAIL-άρει εκεί απορρίπτεται έτσι κι αλλιώς από την πύλη build, οπότε καλύτερα να τη δεις πριν από το Apply παρά μετά.

Οι στόχοι χωρίζονται σε δύο λίστες προσβάσιμες από πληκτρολόγιο: το **MY APPS** περιέχει τα φορητά/source-tree εργαλεία CodeNomad, SAIPENVIEW, SmartVac και WildRift· το **POPULAR APPS** περιέχει τα Windows, το OBS, τα τερματικά, τους επεξεργαστές και το υπόλοιπο εγκατεστημένο λογισμικό. Το ALL/NONE και το Apply/Revert λειτουργούν και στις δύο λίστες χωρίς να αλλάζουν την ομαδοποίησή τους.

Το παράθυρο φοράει την παλέτα που πρόκειται να εγκαταστήσει. Αυτή είναι η ταχύτερη διαθέσιμη προεπισκόπηση και κρατά το εργαλείο τίμιο: μια παλέτα που κάνει αυτό το παράθυρο δυσανάγνωστο είναι εμφανώς δυσανάγνωστη.

Το Apply καλεί το `install.ps1`. Υπάρχει ακριβώς ένα μονοπάτι κώδικα που εγκαθιστά θέμα, οπότε το GUI δεν μπορεί να αποκλίνει από τη γραμμή εντολών.

## Η γραμμή εντολών

```powershell
.\desktop\install.ps1                                  # τι υπάρχει εδώ, τι έχει θέμα, με ποια παλέτα
.\desktop\install.ps1 -Target freebuff -Palette klite  # μία εφαρμογή, μία παλέτα
.\desktop\install.ps1 -Target all -Palette goldendefault # τα πάντα
.\desktop\install.ps1 -Target all -WhatIf              # πες τι θα άλλαζε, μην αγγίξεις τίποτα
.\desktop\install.ps1 -Target freebuff -Revert         # ακύρωσε ένα
```

Το `-Palette` είναι από προεπιλογή `goldendefault` (**Golden Default**). Το GUI ανοίγει στην ίδια παλέτα και ελέγχει κάθε διαθέσιμο στόχο. Το επαναχρωμάτισμα μιας εφαρμογής που έχει ήδη θέμα λειτουργεί ενώ τρέχει· μια πρώτη εγκατάσταση όχι, γιατί το αρχείο είναι σε χρήση.

### Αφαίρεση διαφημίσεων FreeBuff

Το FreeBuff (η desktop εφαρμογή του AI βοηθού) φέρνει το δικό του δίκτυο διαφημίσεων: το bundle του renderer (`resources/orchestrator/ui/assets/index-*.js`) αποδίδει μια κάρτα `sponsored-ad` και ένα banner στο thread, και ο orchestrator (`resources/orchestrator/orchestrator.js`) εκθέτει τις διαδρομές `/api/ad/slot|impression|click` που καλούν τη απομακρυσμένη δημοπρασία διαφημίσεων. Το shim μόνο θέτει θέμα στην εφαρμογή· δεν αγγίζει αυτά τα αρχεία.

Το `desktop/patch-freebuff-ads.js` κόβει τις διαφημίσεις σε επίπεδο byte:

- renderer: τα σημεία κλήσης της κάρτας/banner διαφήμισης γίνονται `null`, και οι μέθοδοι του client API `adSlot` / `adImpression` / `adClick` γίνονται no-op — δεν αποδίδεται τίποτα, και κανένα αίτημα `/api/ad/*` δεν φεύγει από τον renderer·
- orchestrator: και οι τρεις διαδρομές `/api/ad/*` σταματούν να καλούν το δίκτυο διαφημίσεων, και το inline αίτημα διαφήμισης του live turn (`maybeRequestAd`) είναι βραχυκυκλωμένο.

Το όνομα του bundle ενσωματώνει ένα hash build, οπότε το patch ανακαλύπτει το τρέχον bundle από το `index.html` αντί να φορτώνει ένα payload δεσμευμένο σε έκδοση — αυτό το κάνει να επιβιώνει των ενημερώσεων. Τα πρωτότυπα γίνονται backup στο `_orig-backup-<timestamp>/` μέσα στον κατάλογο εγκατάστασης· το `--revert` επαναφέρει το νεότερο.

**Οι μελλοντικές εκδόσεις αντιμετωπίζονται σε δύο ανεξάρτητα επίπεδα:**

1. **Byte patch με fallback regex.** Κάθε στόχος έχει ένα ακριβές string για το τρέχον build *και* ένα fallback κανονικής έκφρασης αγκυρωμένο σε ό,τι δεν μπορεί να μετονομάσει ένας minifier — τα path literals `/api/ad/*`, ο διαχωριστής πρωτοκόλλου `case"ad":`, η κλάση `sponsored-ad` και οι τοποθετήσεις `variant:"banner"` / `variant:"card"`. Ο orchestrator δεν είναι minified (αναγνώσιμα ονόματα όπως `maybeRequestAd` και `app.ads.slotAd`), οπότε τα ακριβή strings του αντέχουν για καιρό· το bundle του renderer είναι minified, οπότε τα fallback regex αναλαμβάνουν τη στιγμή που το επόμενο build μετονομάσει τους αναγνωριστές του.
2. **Μπλοκάρισμα σε επίπεδο shim (`targets/electron/shim.cjs`).** Εντελώς ανεξάρτητο από το bundle: κάθε fetch/XHR προς URL `/api/ad/` απορρίπτεται μέσα στη σελίδα, και κάθε στοιχείο του οποίου η κλάση περιέχει `sponsored-ad` κρύβεται τη στιγμή που εμφανίζεται. Ακόμα και ένα εντελώς καινούριο bundle που αυτό το script δεν έχει μάθει ακόμα δεν μπορεί να αναδείξει διαφήμιση.

```powershell
node .\desktop\patch-freebuff-ads.js           # patch (πρώτα κάνει backup)
node .\desktop\patch-freebuff-ads.js --sound "C:\...\my.mp3"   # patch + προσαρμοσμένος ήχος ολοκλήρωσης (wav/mp3/ogg/flac/m4a/aac)
node .\desktop\patch-freebuff-ads.js --scan    # τι δείκτες διαφημίσεων φέρει ΑΥΤΟ το build;
node .\desktop\patch-freebuff-ads.js --verify
node .\desktop\patch-freebuff-ads.js --revert
```

Τρέχει αυτόματα ως μέρος του `install.ps1 -Target freebuff` και πρέπει να ξανατρέξει μετά από κάθε ενημέρωση FreeBuff (οι ενημερώσεις επαναφέρουν τα τυπικά αρχεία). Αν ένα build αλλάξει σχήμα, το script ονομάζει τον στόχο που δεν ταίριαξε πια — τρέξε `--scan` για να δεις τι φέρει ακόμα το νέο build και ανανέωσε τα strings εκεί.

**Ήχος ολοκλήρωσης FreeBuff.** Ο renderer παίζει `chime-<hash>.mp3` όταν τελειώνει ένα turn. Το patch το βρίσκει με τον ίδιο τρόπο που βρίσκει το bundle (το όνομα ενσωματώνει hash build), οπότε το `--sound <file>` εγκαθιστά το δικό σου ήχο (wav/mp3/ogg/flac/m4a/aac) από πάνω του και κρατά το τυπικό αρχείο ως `chime-*.mp3.bak`· το `--revert` το επαναφέρει. Το `--verify` αναφέρει ποιο είναι ζωντανό.

### Κουμπί ήχου FreeBuff (GUI)

Το `WintageInstaller.ps1` έχει ένα μικρό κουμπί **FB SOUND** κάτω από τη στοίβα APPLY / REVERT. Αποθηκεύει μόνο μια *προτίμηση*· το `install.ps1 -Target freebuff` διαβάζει το ίδιο αρχείο και το δίνει στο patch ως `--sound`, οπότε οι διαφημίσεις και ο ήχος εφαρμόζονται σε ένα τρέξιμο:

- **Αριστερό κλικ** — διάλεξε αρχείο ήχου (OpenFileDialog, wav/mp3/ogg/flac/m4a/aac) και άκουσέ το να παίζει αμέσως: PCM WAV μέσω System.Media.SoundPlayer, κάθε άλλη μορφή μέσω WPF MediaPlayer (Media Foundation, async, οπότε το παράθυρο δεν παγώνει ποτέ). Η επιλογή θυμάται στο `%APPDATA%\Wintage\freebuff-sound.txt` (ανά μηχάνημα, εκτός του git checkout, ακριβώς όπως οι θυμημένοι φάκελοι source-tree).
- **Δεξί κλικ** — σβήνει την προτίμηση πίσω στο τυπικό chime του FreeBuff (σταματά και όποια προεπισκόπηση παίζει ακόμα).
- **COPY** — αντιγράφει τον επιλεγμένο ήχο στο ίδιο το repo (`sounds\freebuff.<ext>`, διατηρώντας την επέκταση της πηγής) και ανακατευθύνει την προτίμηση σε εκείνο το αντίγραφο, οπότε ο ήχος επιβιώνει αν το αρχικό αρχείο διαγραφεί ή μετακινηθεί. Ενεργό μόνο όσο έχει οριστεί προσαρμοσμένος ήχος· το νέο αντίγραφο απλώς αντικαθιστά το αντίγραφο του repo. Ο φάκελος `sounds/` είναι κανονικό περιεχόμενο με git tracking, οπότε το commit τον κάνει να επιβιώσει και στα re-clone.

Μόνο αναγνωρισμένα audio containers προεπισκοπούνται — η κεφαλίδα ελέγχεται πρώτα, οπότε μια μη-ήχου επιλογή ανακοινώνεται αντί να μην παίζει σιωπηλά τίποτα.

Το κουμπί δείχνει **ON** όσο έχει οριστεί προσαρμοσμένος ήχος· hover πάνω του δείχνει τη διαδρομή. Εφάρμοσε μετά τον στόχο `freebuff` (τσεκάρισε FreeBuff + APPLY, ή τρέξε `install.ps1 -Target freebuff` από τερματικό) για να τεθεί σε ισχύ.

### Τερματικά

Το `terminal` γράφει ένα χρωματικό σχήμα `Wintage` σε κάθε ανιχνευμένο σταθερό, Preview ή μη-συσκευασμένο αρχείο ρυθμίσεων Windows Terminal και το επιλέγει μέσω `profiles.defaults`, μαζί με ασφαλή για κονσόλα Consolas 12 και aliased κείμενο. Το αρχικό αρχείο διατηρείται byte-προς-byte δίπλα του, και το `-Revert` το επαναφέρει.

Το `conhost` καλύπτει το κλασικό `cmd.exe`, τα Windows PowerShell, τα προφίλ κονσόλας Git CMD/Bash και άλλα υπάρχοντα παιδιά `HKCU\Console`. Γράφει τον πλήρη πίνακα 16 χρωμάτων της παλέτας τόσο στις προεπιλογές ρίζας όσο και σε κάθε υπάρχουσα παράκαμψη, και μετά επαναφέρει μόνο τις τιμές που άγγιξε. Εφαρμόζει και εδώ Consolas, γιατί η αναλογική Verdana συγκρούεται μέσα στο πλέγμα κελιών σταθερού πλάτους που χρησιμοποιούν και οι δύο hosts τερματικών.

### Browsers και Tampermonkey

Το `browsers` βρίσκει προφίλ Chrome, Edge, Brave, Cent, Vivaldi και Opera από εγκατεστημένες τοποθεσίες και από τη φορητή ρίζα στην οποία το δείχνεις (`-PortableRoot`, ή η θυμημένη καταχώρηση `portable` στο `paths.json`). Η κατάστασή του δείχνει και τον αριθμό προφίλ και πόσα περιέχουν Tampermonkey. Το Apply αντιγράφει το επιλεγμένο browser-chrome θέμα στον σταθερό φάκελο `%LOCALAPPDATA%\Wintage\browser-theme`, βάζει αυτή τη διαδρομή στο πρόχειρο, και ανοίγει κάθε ακριβές προφίλ στο `chrome://extensions` συν τη σελίδα Install/Update του userscript Wintage. Τα προφίλ χωρίς Tampermonkey παίρνουν και τη σελίδα του στο Chrome Web Store.

Το Chromium απαγορεύει εσκεμμένα τη σιωπηλή εγκατάσταση extensions εκτός καταστήματος σε μη διαχειριζόμενο Windows μηχάνημα. Η πρώτη εγκατάσταση θέματος browser χρειάζεται λοιπόν μία επιβεβαίωση **Developer mode → Load unpacked** ανά προφίλ. Διάλεξε την αντιγραμμένη διαδρομή· μετά από αυτό, το Wintage συνεχίζει να αντικαθιστά τον ίδιο σταθερό φάκελο όταν αλλάζουν οι παλέτες. Επιβεβαίωσε και το **Install/Update** στο Tampermonkey. Κανένα αρχείο `Preferences`, Secure Preferences ή Tampermonkey LevelDB του browser δεν επεξεργάζεται πίσω από την πλάτη του. Αν το Tampermonkey δεν υπήρχε, εγκατέστησέ το από το ανοιχτό tab του καταστήματος και ανανέωσε το ήδη ανοιχτό tab `wintage.user.js` για να πάρεις την οθόνη Install.

### Windows

Το `windows` εγκαθιστά και ενεργοποιεί αμέσως ένα αρχείο `%LOCALAPPDATA%\Microsoft\Windows\Themes\Wintage-<hash>.theme` που διευθύνεται κατά περιεχόμενο. Ξεκινά από το ενεργό θέμα και αντικαθιστά μόνο τις τεκμηριωμένες ενότητες χρωμάτων, κέρσορα και οπτικού στυλ. Η ταπετσαρία, οι ήχοι και τα εικονίδια επιφάνειας εργασίας μένουν αμετάβλητα· οι κέρσορες αλλάζουν σκόπιμα στο εγκατεστημένο σχήμα `___CURRENT___`. Το πρώτο ενεργό θέμα αποθηκεύεται byte-προς-byte ως `Wintage.original.theme`· οι αλλαγές παλέτας κρατούν αυτή τη γραμμή βάσης, και το `-Revert` το ενεργοποιεί ξανά. Τα σύγχρονα controls των Windows έρχονται πάντως από το υπογεγραμμένο οπτικό στυλ Aero — το Wintage αλλάζει τις υποστηριζόμενες εισόδους του για σκούρη λειτουργία, accent και κλασικά χρώματα συστήματος, αντί να αντικαθιστά προστατευμένα αρχεία `.msstyles`. Οι ενεργές και ανενεργές λεζάντες μοιράζονται το σκούρο ανασηκωμένο χρώμα επιφάνειας της παλέτας· το φωτεινό highlight μένει αποκλειστικό για τις άκρες κειμένου/επιλογής. Το προηγούμενο accent της ανενεργής λεζάντας παίρνει ξεχωριστό snapshot και επαναφέρεται ακριβώς από το `-Revert`. Το hash περιεχομένου δίνει στα Windows νέο στόχο συσχέτισης αρχείων όταν η ίδια παλέτα ξαναχτιστεί, οπότε το re-apply μιας ενημερωμένης παλέτας δεν μπερδεύεται με no-op· το ξεπερασμένο αρχείο Wintage αφαιρείται αφού τα Windows επιβεβαιώσουν το νέο ως ενεργό.

### OBS Studio

Το `obs` δημιουργεί μια παραλλαγή OBS 30.2+ πάνω στη συντηρημένη βάση Yami Classic, την εγκαθιστά στο `%APPDATA%\obs-studio\themes` και γράφει το σταθερό ID θέματός της στο `user.ini`, οπότε η επιλεγμένη παλέτα Wintage είναι ήδη επιλεγμένη στην επόμενη εκκίνηση. Κλείσε το OBS πριν το Apply ή το Revert: το OBS ξαναγράφει το `user.ini` στην έξοδο. Η πρώτη εφαρμογή κάνει backup byte-προς-byte τόσο της προηγούμενης επιλογής όσο και κάθε θέματος με το ίδιο όνομα.

### Εφαρμογές Electron

Το `resources/app.asar` μετακινείται σε `resources/app/app.asar` (το αδερφάκι του `app.asar.unpacked` μετακινείται μαζί — αυτό το ζευγάρωμα είναι κατά όνομα αρχείου, και ο χωρισμός τους σπάει κάθε native module), και ένα μικρό `shim.cjs` παίρνει την εκκενωμένη θέση `resources/app`. Το shim εισάγει το stylesheet και μετά φορτώνει το αρχικό αρχείο. **Κανένα byte της εφαρμογής δεν ξαναγράφεται**, μόνο μετατοπίζεται· το `-Revert` το μετακινεί κατευθείαν πίσω.

Το stylesheet δεν γράφεται για αυτές τις εφαρμογές — εξάγεται από το `wintage.user.js`, οπότε κάθε διόρθωση bevel, scrollbar και κλίμακας τυπογραφίας που γίνεται για τον browser φτάνει και εδώ, χωρίς δεύτερο αντίγραφο που να σαπίζει.

Δύο σημειώσεις που αξίζει να γνωρίζεις εκ των προτέρων:

- Η προφανής προσέγγιση — να ρίξεις το `resources/app` δίπλα στο αρχείο και να βασιστείς στο Electron ότι θα το προτιμήσει — **δεν λειτουργεί και αποτυγχάνει σιωπηλά**. Το Electron ψάχνει πρώτα το `app.asar`. Η εφαρμογή ξεκινά τέλεια και το θέμα δεν τρέχει ποτέ.
- Το shim είναι `.cjs`, όχι `.js`, επίτηδες. Το `package.json` του αντιγράφεται από της εφαρμογής, οπότε η εφαρμογή κρατά το όνομα και την έκδοσή της (το όνομα αποφασίζει πού ζει το userData — ένα shim που το μετονομάζει μετακινεί την εφαρμογή σε κενό προφίλ). Αν αυτό το manifest λέει `"type": "module"`, ένα shim `.js` πεθαίνει στο πρώτο του `require`.

### Η desktop εφαρμογή του Claude: στη θέση της, και το πλαίσιο στο οποίο πραγματικά ζωγραφίζει

Το Claude δεν μπορεί να χρησιμοποιήσει την παραπάνω μετατόπιση, γιατί το `OnlyLoadAppFromAsar` είναι fused-on — το Electron φορτώνει το `resources/app.asar` και τίποτα άλλο, οπότε ένα shim στο `resources/app` δεν μπορεί ποτέ να τρέξει. Γίνεται patch **στη θέση του** αντί αυτού: το αρχείο γίνεται backup, το `main` του `package.json` ξαναγράφεται σε `"../wintage-shim.cjs"` (με padding στο ίδιο μήκος byte, ώστε κάθε offset στο αρχείο να μένει έγκυρο), και το hash ακεραιότητας ανά αρχείο ενημερώνεται για να ταιριάζει. Το `-Revert` επαναφέρει το backup.

Ο εγκαταστάτης διαβάζει πάντως τα fuses **πριν μετακινήσει οτιδήποτε** και αρνείται με αιτιολογία όταν τον μπλοκάρουν — το `EnableEmbeddedAsarIntegrityValidation` θα έκανε το παραπάνω ξαναγράψιμο να αποτύχει στην εκκίνηση αντί στην εγκατάσταση. Έλεγξε όποια εφαρμογή μόνος σου:

```powershell
node ..\tools\electron-fuses.js "<path to the app's exe>"
```

Το δεύτερο μισό αυτού ήταν πολύ πιο ήσυχο πρόβλημα. Το `BrowserWindow` του Claude αποδίδει ένα λεπτό κέλυφος και **ολόκληρη η ορατή εφαρμογή είναι ένα `WebContentsView`** προσαρτημένο σε αυτό. Το shim συνήθιζε να κάνει hook το `browser-window-created`, οπότε έκανε ένεση του stylesheet στο κέλυφος, ανέφερε επιτυχία στο `wintage-status.txt` και δεν άλλαζε τίποτα ορατό. Τώρα κάνει hook το `web-contents-created`, που καλύπτει το περιεχόμενο παραθύρων, τα `WebContentsView`, τα `BrowserView`, τους καλεσμένους `<webview>` και τα popups εξίσου.

### Obsidian

Ένα θέμα κοινότητας γράφεται στο `.obsidian/themes/` κάθε vault — και οι δεκαέξι παλέτες μαζί, ακριβώς όπως ο στόχος VS Code, οπότε εναλλάσσεσαι μεταξύ τους στο **Settings → Appearance** χωρίς να ξανατρέξεις τίποτα. Το πρότυπο προήλθε από το χειροποίητο θέμα `VintageWin95` που υπάρχει ήδη στο vault, με κάθε χρώμα αντικατεστημένο από το token στο οποίο αντιστοιχούσε. Το `-Palette <slug>` ορίζει ποιο είναι ενεργό στην εγκατάσταση· το `appearance.json` παίρνει backup πρώτα, και το `-Revert` αφαιρεί μόνο τα θέματα `Wintage *` και επαναφέρει την προηγούμενη επιλογή σου — ένα χειροποίητο θέμα στο ίδιο vault δεν αγγίζεται ποτέ.

### SAIPENVIEW

Το frontend του δηλώνει ήδη τα ονόματα tokens του Wintage στο δικό του `:root`, οπότε αυτό το patch ξαναγράφει **μόνο τις τιμές tokens** — ποτέ έναν selector, ένα font, ένα πλάτος border ή ένα padding. Τίποτα που επηρεάζει το box model δεν αλλάζει, οπότε το κείμενο δεν μπορεί να μετατοπιστεί. Αυτό είναι εσκεμμένο: η προηγούμενη προσέγγιση προσάρτησε ολόκληρο το stylesheet του browser από πάνω, και το `wintage.css` είναι γραμμένο για αυθαίρετες ιστοσελίδες — καθολικοί selectors που επιβάλλουν το font, την κλίμακα μεγεθών, borders 2px και ύψη controls. Σε μια εφαρμογή που έχει ήδη το δικό της layout, αυτό μετακινεί τα πάντα.

Επαληθευμένο με μάσκα κάθε hex και diff με το backup: δομικά πανομοιότυπο, διαφέρουν μόνο τα χρωματικά literals. Το `--link` αναφέρεται ως μη δηλωμένο εκεί (τα markdown links του διαβάζουν `--accentTeal`, το οποίο αυτό θέτει) αντί να γίνει ένεση — το να προσθέσεις μια μεταβλητή που η εφαρμογή δεν διαβάζει ποτέ θα ήταν νεκρό βάρος.

### MPC-HC (K-Lite)

Native Win32, χωρίς stylesheet και χωρίς σημείο ένεσης, και τα χρώματα του σκούρου θέματός του είναι μεταγλωττισμένα στο πρόγραμμα — καμία τιμή registry δεν τα εκθέτει. Οπότε αυτός ο στόχος **δεν μπορεί να φέρει παλέτα**. Τι κάνει: ενεργοποιεί το σκούρο θέμα και εφαρμόζει τους κανόνες τυπογραφίας του UI.md στο OSD, που είναι η μόνη επιφάνεια που το MPC-HC επιτρέπει να ελέγχει ο χρήστης. Οι προηγούμενες ρυθμίσεις εξάγονται πρώτα στο `desktop/backup/mpc-hc-settings.reg`.

Κλείσε το MPC-HC πριν την εφαρμογή: ξαναγράφει τις ρυθμίσεις του στην έξοδο.

## Ανακατασκευή

Ό,τι βρίσκεται κάτω από το `desktop/out/` παράγεται από το `themes/*.json`. Δεν παρακολουθείται στο git (T-160), οπότε ένα φρέσκο clone πρέπει να το χτίσει μία φορά πριν εγκαταστήσει:

```powershell
node ..\tools\build-desktop.js          # ξαναχτίσε όλους τους στόχους
node ..\tools\build-desktop.js --check  # exit code 1 αν κάτι είναι ξεπερασμένο
```

Το `release.ps1` τρέχει το build και κάθε πύλη, οπότε μια κυκλοφορία δεν μπορεί να στείλει output που έχει αποκλίνει από τις παλέτες.

# ADR-002 — The sweeper must never interleave computed-style reads with style writes

Status: ACCEPTED (26.07.26, shipped v1.3.0)
Supersedes nothing. Related: [[ADR-001]] (animation taming).

## Context

Reported symptoms: ~10% CPU with every tab idle, and sites that need two or three
reloads before they come up properly.

`process()` was written as one loop per element: read `getComputedStyle(el)`,
decide, then immediately `setImp(el, ...)` inline styles. That reads naturally and
is how almost every restyling userscript is written. It is also, specifically for
*this* theme, close to the worst possible shape.

Every inline style write invalidates style. The next element's `getComputedStyle`
therefore cannot be served from cache — it forces a fresh style resolution. And
this theme's own CSS makes that resolution unusually expensive, because it is
built out of exactly the selectors engines optimize worst:

- `* { border-radius: 0 !important }`
- `*, *::before, *::after { … }` (the motion rule)
- `*:not(svg):not(path):not(i):not([class*="icon" i]):not([class*="fa-" i]):not([class*="symbols" i]):not([class*="glyph" i]):not([class*="mdi" i]):not([class*="bi-" i])` — eight case-insensitive attribute-substring matches per element, for the forced Verdana
- `:root body *:hover:not(button):not(a)…:not(:active):not(:focus)` — twelve negations, for the hover-highlight freeze

So one write bought one full-document recalc, and the sweeper did 2500 writes per
force pass.

## Measurement

Live, `en.wikipedia.org/wiki/World_War_II`, 16921 elements, published v1.2.1
eval'd into the real page (not a synthetic benchmark):

| pattern, 2500 elements | time |
|---|---|
| reads only | 70.6 ms |
| interleaved read + write (v1.2.1) | 1069–1994 ms |
| batched read-then-write | 230.9 ms |
| — of which ONE whole-document recalc | ~190 ms |

An instrumented real `setInterval(1500)` tick measured **253 ms**, i.e. **16.9 %
of a core, permanently, on a settled page**. Boot was one **716 ms** long task.

The batched figure is the floor: ~190 ms of its 231 ms is a single unavoidable
recalc. There is no cheaper way to re-verify a 17k-element page under this CSS;
the only thing that was ever wasteful was doing that recalc 2500 times.

## Decision

1. **`process()` only reads.** Every style change is appended as an
   `[el, prop, val]` triple to a caller-owned flat queue; the caller calls
   `flushWrites()` once at the end of the whole sweep (across all shadow roots
   too, one queue for the lot). N recalcs become 1.
2. **Attribute writes stay inline** — `data-w95-done` is referenced by no
   selector in this theme so it invalidates nothing (6.7 ms for all 16921
   elements), and `removeAttribute('bgcolor'/'background')` is a no-op when the
   attribute is absent.
3. **Force sweeps become demand-driven.** They used to run every 3rd tick
   (~4.5 s) forever regardless of whether anything had changed. Now
   `requestForceSweep()` is called on: new DOM nodes, a changed stylesheet, a
   return from a hidden tab, and a slow 30 s heartbeat. Light sweeps stay
   unconditional because they are genuinely free (0.7 ms on a settled page —
   `*:not([data-w95-done])` matches nothing).
4. **Attribute churn must NOT request a force sweep.** A spinner toggling
   classes would otherwise keep the expensive pass alive forever. Attribute
   mutations already clear `data-w95-done`, so the cheap light sweep picks the
   element up on its own.
5. **Sub-frames get no interval.** With `@match *://*/*` at `document-start` the
   whole engine ran once per iframe. Frames keep the CSS and the (idle-free,
   event-driven) MutationObserver plus three bounded settling sweeps. `@noframes`
   was rejected — it would leave every embed an unthemed white rectangle.
6. **Mutation batches are de-duplicated.** The parser and SPA hydration report a
   container *and* its descendants as separate `addedNodes` records in the same
   batch; the old loop walked every record's full subtree and even cleared
   `data-w95-done` first, guaranteeing the redundant re-read. Now a record with
   an added ancestor in the same batch is skipped (walk up `parentNode`, O(depth),
   never O(batch²)), as are nodes already detached again.

## Result (same page, same method, v1.3.0)

- boot long task: 716 ms -> **327 ms**
- light tick: **0.8–1.3 ms**; force tick: 250 ms -> **19–42 ms**
- average tick: **19.2 ms = 1.28 % CPU** while still settling, **0.09 %** once settled
- correctness: 996 sampled elements compared across a reload, v1.2.1 vs v1.3.0,
  on `color` + `background-color` + `border-top-color` -> **0 differences**
- 37 light backgrounds remain, all `IMG` — deliberately in `TAG_SKIP`

## Consequences / traps for future work

- **Batching changes read ordering for inherited properties.** A child no longer
  sees its parent's just-corrected `color` while being read, so it fails the
  contrast check against the *original* inherited value and gets its own explicit
  inline color. Same final pixels, one extra declaration — it can never resolve
  to a *different* color. Non-inherited properties (background, border-*) are
  unaffected. The 996-element diff above is the evidence, not the argument.
- **Never add `style` to the observer's `attributeFilter`.** `setImp` writes
  inline styles, so the observer would fire on its own output and spin. This is
  why the 30 s heartbeat exists at all: a site mutating an existing element's own
  `style`/custom properties is invisible to the observer, and the old blind 4.5 s
  force pass healed that case by accident. Removing the blind pass without
  replacing it would have been a real regression, so it was kept — 20x rarer.
- **Any new rule added to `GLOBAL_CSS` with a `*` or multi-`:not()` shape raises
  the cost of every single recalc, everywhere.** That cost is now paid once per
  sweep instead of 2500 times, which hides it — do not read the improved numbers
  as headroom for more universal selectors.
- **`requestForceSweep()` owes a whole lap, not one pass.** Force passes are
  budgeted to a rotating 2500-element window, so a single pass would never
  finish a lap on a big page and everything past the first 2500 elements would
  never be re-verified. The debt is capped at 8 passes.

# ADR-004 — `animation-duration: 0.001s` does not stop an infinite animation, it strobes it

Status: ACCEPTED (26.07.26, shipped v1.4.1)
Corrects one claim in [[ADR-001]]. Related: [[ADR-003]] (UI.md deviations).

## Context

The user asked: with `animation-duration: 0.001s`, does an infinite animation now
replay a billion times faster and more? Yes. The theme had this wrong since
v1.2.0, and [[ADR-001]] signed off on it with an incomplete check.

ADR-001's claim was: *"Infinite animations (spinners): Chromium coalesces
animationiteration to at most one per frame, so no event flood."* That is about
**events**. It says nothing about what the animation renders, and the conclusion
"so this is fine" was drawn from the event half alone.

## Measurement

Web Animations API, on a real spinning element, no compositing required (the
engine computes iteration and progress on demand, so this is exact rather than
sampled). Two identical `rotate(0deg) -> rotate(360deg)` animations, one at the
site's intended `1s`, one at the forced `1ms`, both `iterations: Infinity`:

| | site intended, 1s | forced, 0.001s |
|---|---|---|
| `currentIteration` after 1 frame (16.7ms) | 0 | **16** |
| `currentIteration` after 1 second | 1 | **1000** |
| iterations per 60fps frame | 0 | **16.7** |

Angle actually rendered on six consecutive 60fps frames:

| frame | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 1s | 6° | 12° | 18° | 24° | 30° | 36° |
| 0.001s | **240°** | **120°** | **0°** | **240°** | **120°** | **0°** |

A 16.667ms frame divided by a 1ms duration leaves a repeating 2/3 remainder, so
the spinner does not freeze — it **strobes between exactly three rotations,
forever**. Worse than the smooth spin it replaced, and it makes the theme's
headline "zero animations" claim false.

Note on cost: this is NOT 16x the rendering work. The engine samples an animation
once per frame regardless of duration, computing `progress = (t mod d) / d` — it
does not evaluate the 16 intermediate iterations. So the problem is visual, not
CPU. The event-flood question from ADR-001 remains **unverified here** — measuring
it needs real animation frames, which the headless pane does not produce. It is
also now moot for infinite animations, which no longer run at all.

## Decision

Keep `animation-duration: 0.001s` globally for **finite** animations — that is
what makes reveals instant while keeping `animationend` firing, which is the whole
point of ADR-001 and remains correct.

For **infinite** animations, force `animation-play-state: paused` from the JS
repainter instead.

Three things make this safe rather than a rerun of the v1.0.9 mistake:

1. **An infinite animation's `animationend` never fires.** Keeping `animationend`
   alive is the entire reason 0.001s was chosen over `0s`/`none` (ADR-001). No
   `animationend`-driven state machine can possibly be waiting on an animation
   that has no end, so the compromise buys nothing here and the risk it was
   protecting against does not exist.
2. **`paused`, not `animation: none`.** A paused animation keeps applying its
   current computed value. Cancelling would snap the element back to its base
   state, which for a pulse/skeleton loop is frequently `opacity: 0` — i.e. it
   would make content disappear. This is the same class of error as the v28
   `opacity: 1` force-reveal bug, in the opposite direction.
3. **CSS cannot express it.** There is no selector for
   `animation-iteration-count: infinite`, so the check must read computed style,
   which means JS.

## Implementation trap

The check runs **before** `shouldSkip()`, and that is load-bearing. The two
commonest real spinner shapes are both already in the skip set:

- Tailwind's `<svg class="animate-spin">` — `SVG` is in `TAG_SKIP`
- a spinner inside a loading `<button>` — `shouldSkip` matches `closest('button')`

Placing the check after the skip would have missed exactly the cases that
motivated it. Verified live on all four cases:

| case | result |
|---|---|
| infinite `div` | `paused` |
| infinite `svg` (TAG_SKIP) | `paused` |
| infinite `span` inside `<button>` (shouldSkip) | `paused` |
| **finite** animation | **`running`, untouched** |

## Residual risk, accepted

Code that drives state from `animationiteration` — some marquee and carousel
loops — will stall. Rare, and the alternative is a permanent three-position
strobe on every spinner on the web. If a real site is found broken this way, the
fix is to narrow the pause by hue/size heuristics, **not** to go back to 0.001s.

## Lesson

ADR-001 verified the mechanism it was worried about (event flooding) and treated
that as verifying the outcome (motion stopped). Those are different claims. When
the stated goal is visual ("zero animations"), the verification has to measure
what is on screen — here, the rendered angle per frame — not just the plumbing
underneath it.

# ADR-005 — Observing `style` is correct, but self-write suppression must be by identity

Status: ACCEPTED (27.07.26, shipped v1.4.2)
Supersedes the "never add `style` to attributeFilter" rule in [[ADR-002]].
Related: [[ADR-003]], [[ADR-004]].

## Context

[[ADR-002]] left one hole open and papered over it with a timer: a site mutating
an existing element's **own inline `style`** is invisible to the observer, because
`style` was deliberately excluded from `attributeFilter` — `setImp` writes inline
styles, so the observer would be handed its own output. ADR-002's compensation was
a 30-second polling `requestForceSweep()` heartbeat.

Polling is exactly what "no idle CPU" cannot afford. The right move is to observe
`style` for real and delete the heartbeat — which requires making self-write
suppression actually airtight, not merely usually-true.

## The first attempt, and why it was wrong

Suppression by time window: `flushWrites()` set `selfStyleMuteUntil = now + 100`,
and the mutation handler dropped any `style` record arriving inside that window.

Measured on a static article (16595 elements), 12-second window:

| | style mutation records |
|---|---|
| site alone, no theme | **0** |
| with the theme | **9466** |

Every single record was self-inflicted. The mute did discard them, so there was no
visible runaway — but all 9466 were still allocated, delivered through a
microtask, and pushed into `pendingMuts` for the next debounce to walk.

Worse, it was only timing-safe by luck. The filter runs at the **end** of the 60ms
debounce, not at push time. Any flush landing more than 100ms before its debounce
fires — i.e. precisely when the main thread is busy, i.e. precisely during a heavy
sweep — lets our own writes through. Each one that gets processed clears
`data-w95-done`, re-processes the element, and generates more writes: the exact
feedback spin ADR-002 banned the field to avoid, now merely rarer and
load-dependent. A blanket window also drops the **site's** real style changes for
100ms after every sweep.

## Decision

Suppress by identity, and drain the queue before the callback ever sees it:

1. `flushWrites()` records every element it writes into a `Set`.
2. It then calls `takeRecords()` on both observers — which returns **and clears**
   the pending queue, so this runs before any callback is invoked for those
   mutations.
3. Records that are `style` changes on elements in the Set are dropped. Everything
   else — foreign `style` changes, `class` changes, `childList` records that
   happened to be queued alongside — is pushed back into `pendingMuts`.
4. If anything was kept and the debounce is not already armed, re-arm it.

Timing-independent, and scoped to the exact elements involved.

## Result (v1.4.2, 13075 elements + 200 planted shadow roots)

| | before | after |
|---|---|---|
| self-inflicted style records / 12s | 9466 | **0** |
| foreign style change still caught | — | **yes** (see below) |
| settled light sweep | 1.1–1.4 ms | 1.1–1.4 ms |
| backoff ladder actually reached | 1500 (stuck) | 1500 → 3000 → 6000 → 12000 → 24000 → 60000 |

Regression test for the risk this change introduces (throwing away foreign records
along with our own): a `background-color: #ffffff !important` plus
`color: #ffffff !important` written inline onto a live element, the way a site
would. Theme reacted and repainted it to `rgb(30,20,8)` = `--backgroundSoft`, text
to `rgb(212,184,122)` = `--textPrimary`. Foreign writes are still seen.

## Accepted gap

A site style-change on an element **we also wrote to in the same batch** is
dropped. Self-healing: the next sweep re-reads that element's computed style from
scratch. This is a bounded, one-sweep delay, traded for eliminating an unbounded
feedback path.

## Things measured and deliberately NOT changed

- **The backoff was never broken.** It looked stuck at 1500ms because
  `forcePassesOwed` starts at 7 on a 16k-element page (one lap ÷ 2500 budget) and
  only decrements on every 3rd tick, so it pins the cadence for ~21 ticks (~31s)
  after each request. A 12-second measurement window simply ended inside that
  drain. Over 53s it climbs the ladder correctly. No change made.
- **Draining the force debt faster** (force on every tick instead of every 3rd)
  would shorten the elevated window from ~31s to ~10s, but on an
  actively-mutating page where the debt keeps being topped up it turns a sustained
  0.9% into a sustained 2.7%. Measured cost of the current behaviour is ~1% for
  31s and then effectively zero, so the trade is not worth it. Left alone.
- **Per-shadow-root sweeping costs nothing.** With 200 pierced roots the light
  sweep measured 1.0–1.5ms — the same as with none. A `dirtyRoots` gating scheme
  was considered and rejected: it would add real complexity for no measurable win.
  Do not "optimise" this without a measurement showing it matters.

## Lesson

Suppressing your own side effects by "it probably happened within N milliseconds"
is not suppression, it is a race with a comfortable-looking constant. If you can
name the exact objects you touched, filter on those.

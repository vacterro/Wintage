# ADR-009 — A delivery claim names a path the artifact contains

Date: 2026-10-05. Ticket T-417 (improve cycle imp-vacterro-wintage-20261005-4, RUN-1/IMP-004).

## Context

The T-413 delivery report listed "the npm test/test:bd script repair" as part of
the deliverable. The repair was made in `package.json`, which `.gitignore:60`
excludes, which has no git history, and which no release archive contains. The
claim was therefore unopenable from the artifact and read as stale narration
from another working environment; the operator said exactly that when reviewing
the release, and did not count the line as evidence. Nothing in the pipeline
compared what a report CLAIMED against what the artifact CONTAINS: the digest is
written by hand at SHIP and was never read back programme.

The tempting rule -- "check the file exists" -- is the one that fails here,
because the file did exist, in the working copy, with the edit applied. The
working copy is not the deliverable.

## Decision

A path named in the delivery text is a claim about the artifact. It must resolve
in the artifact: present in `HEAD`, or staged for the commit being written,
since `release.ps1` builds the archive from tracked files. `tools/check-delivery-claims.ps1`
enforces that on `.saipen/kitchen/digest.md` by default, or on any report passed
with `-Path`, and prints every token it could not resolve with the reason -- for
a file that exists but is ignored, the `git check-ignore -v` rule that excluded
it.

Two consequences of the design are deliberate. First, prose mentions are claims
too: a report that names a bare file where it means a path (`LOG.md` for
`.saipen/LOG.md`) is reported, and the fix is to name the real path or to drop
the name -- the alternative, distinguishing claims from mentions by sentence
shape, would make the rule advisory at exactly the moment it matters. Second,
`-Allow` exists so a reporter can declare a non-product path on purpose; a claim
that cannot be verified is then visibly declared rather than silently unverified.

## Consequences

- A report can no longer ship a claim the recipient cannot open without the
  report saying so: the checker is run on the digest at SHIP, and its verdict
  line states how many claims resolved, how many were declared, and how many did
  not.
- The gate is non-vacuous by construction: `-RedControl` builds a scratch
  repository holding a tracked file and an ignored one, and requires the ignored
  claim to be caught (naming the `.gitignore` rule) while the tracked file in
  the same sentence resolves, a claim naming a nonexistent path is caught, a
  declared path is not, and version strings (`1.36.6`, `v1.36.1`) and
  dot-prefixed file names are not mistaken for tokens.
- The real defect is reproducible: the T-413 claim sentence scores its
  `package.json` unverifiable.
- Rewording reports is now part of delivery. That cost is paid where it buys
  something: the recipient of the next report can open every path it names.

# ADR-006 — Sweep rate must have a floor, and CSS cannot enforce UI.md on its own

Status: ACCEPTED (27.07.26, shipped v1.4.3)
Related: [[ADR-002]] (read/write split), [[ADR-005]] (self-write suppression), [[ADR-003]] (UI.md deviations)

## Context

User report: Wintage idling at ~8% CPU on a real chatgpt.com conversation, while
the same theme measured 0.14% on wikipedia. Four hypotheses were tested and three
were wrong; recording them matters as much as the fix, because each looked
obviously right.

## What it was NOT

| hypothesis | how it died |
|---|---|
| Universal `:not([class*="…" i])` selectors are slow against long Tailwind class strings | Benchmarked: current selectors 88ms, an attribute-flag rewrite 91ms, no exclusions at all 79.7ms. The substring matches cost ~10%. |
| Our CSS makes every recalc expensive | Disabling both `style[data-w95]` sheets in place changed nothing: 13532ms of long tasks with CSS on, **13525ms with CSS off**. |
| The `:hover` rule surgery re-walks huge stylesheets | Measured on the live page: full walk of 20945 rules = **22ms**, property enumeration 14ms, sheet objects stable (0 recreated in 10s). |
| The element sweeper is thrashing | `data-w95-done` present on 3060 of 3062 elements, **0** removals in 15s, 51 style + 2 class mutations total. |

Attribution came from the clean control: script disabled entirely = 2517ms of long
tasks; script enabled = 13532ms. So it was our JS, and none of the usual suspects.

## Root cause

Counting the primitives directly (wrapping them on the prototypes from the
console) on the failing page — 3392 elements, 15 seconds:

```
querySelectorAll ....    151 calls   -> ~10 sweeps per SECOND
getComputedStyle ....  42563 calls
Element.closest .....  80114 calls
setAttribute ........  43080 calls
long tasks .......... 14158 ms of 15000 (94% of wall time)
```

`requestForceSweep()` ended in `scheduleNextSweep(true)` — a **0ms** timer — and
it is called from the mutation handler for every batch containing added nodes.
On a React app that inserts nodes continuously, every insertion queued an
immediate full sweep, whose own writes and stylesheet check queued the next one.
Back-to-back sweeps with no floor.

Reproduced locally at 148 sweeps / 15s by driving a wikipedia page with a
100ms DOM-insertion loop, which is what made the fix verifiable.

## Decisions

### 1. A hard floor on sweep rate (the actual safety property)
`MIN_SWEEP_GAP = 1000ms` between the END of one sweep and the START of the next.
Nothing may schedule a sweep at 0ms. A pending timer that fires sooner is never
replaced by a later one and never cancelled-and-re-armed — the old code churned
the timer on every call. The adaptive backoff to 60s remains, but it is only an
idle optimisation on top of the floor, not the protection itself.

Same synthetic churn, before vs after:

| | v1.4.2 | v1.4.3 |
|---|---|---|
| sweeps / 15s | 148 | **11** |
| getComputedStyle | 135823 | **20844** |
| Element.closest | 388194 | **59444** |
| setProperty | 68388 | **11730** |

### 2. UI.md invariants are enforced from JS, because CSS structurally cannot
Our universal rules score specificity (0,0,0). A site's `!important` beats them
with any specificity at all, and an ID rule beats them absolutely — no number of
`:root` prefixes outranks (1,0,0). Measured on stackoverflow.com:

- `a.bar-sm` kept `border-radius: 4px`
- `h1.fs-headline1` kept `font-size: 27px`, `h2.fs-body2` kept 15px
- `#onetrust-banner-sdk` kept its `box-shadow`

Inline `!important` — what `setImp` writes — is the one declaration that outranks
every author rule regardless of selector. So `border-radius: 0`, `box-shadow: none`
and the type ladder are re-asserted from `process()` whenever the computed value
actually disagrees. The check is nearly free (`cs` is already resolved) and the
write is skipped when CSS already won, which is 3348 of 3362 elements.

### 3. Control subtrees get a palette clamp
`shouldSkip` excludes anything under `closest('button')` so our bevels and labels
survive. But `#onetrust-consent-sdk #onetrust-accept-btn-handler {…!important}`
scores (2,0,0) against our `button {…!important}` at (0,0,1), and
`#onetrust-banner-sdk * { color: … !important }` at (1,0,0) beats every universal
colour rule — leaving near-black text on near-black surfaces inside the banner.
Skipped elements now get clamped, but **only when provably off-palette**, so a
correctly themed control is untouched and the skip's original purpose survives.

### 4. Two dark-surface gaps closed
Measured on amazon.com:
- `#nav-belt` `#131921` — grayish (spread 14) but luminance 0.0094, under the old
  0.015 "near-black is left alone" floor.
- `#nav-main` `#232f3e` — spread 27, over the grayish cutoff of 24 but under the
  saturated cutoff of 60, so it fell through **both** branches and was never
  touched at all.

The neutral band widens to spread ≤ 60 and the branches merge; the floor drops to
0.004, which still leaves true black (video players, scrims) alone.

Also: anything inside a link now takes the link colour when it is merely
off-palette, not only when it is unreadable. `span#nav-cart-count` kept `#f08804`
and `span.navFooterDescText` kept `#999999` because both are legible (7.1:1 and
6.3:1). Legible is not the same as on-palette.

### 5. Palette idempotence — the regression fix 4 caused
Widening the dark band made the repainter re-grade **its own output**: our
`--backgroundSoft` (#1E1408, lum 0.0088) and `--surfaceRaised` (#362812, lum
0.0234) both land in the "< 0.05" bucket, so `body` went #1E1408 → #2A1C0A and
dialogs / `th` / hovercards would have followed. The whole surface hierarchy
would have slowly collapsed onto one shade. `--textSecondary` (#B09558, channel
spread 88) would likewise have been flattened to `--textPrimary` by the
"not grayish" branch.

A palette value is by definition already correct: both the background and the
foreground paths now return early when the computed colour is already a token.
Verified by snapshotting six elements, waiting 8s, and re-snapshotting — **zero
drift**.

## Lessons

- **Attribute before optimising.** Three plausible hypotheses were all wrong, and
  each would have produced a real code change that fixed nothing. The
  disable-the-CSS-in-place control took one command and killed two of them at once.
- **Count calls, not milliseconds.** `getComputedStyle` is lazy: wrapping it
  showed 42563 calls costing 19ms, because the cost lands on the property *read*
  that forces recalc. The call count was the signal; the timing was noise.
- **A rate limiter belongs at the scheduler, not at each caller.** Every
  individual `requestForceSweep()` call site was reasonable. The floor is the only
  thing that makes the composition safe.
- **Any normalising transform must be idempotent against its own output.** This
  one was not, and the failure mode was slow and quiet — a hierarchy collapsing
  one shade at a time, invisible in a single screenshot.
